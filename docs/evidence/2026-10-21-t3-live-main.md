## Follow-up

A separate diagnosis (Codex `gpt-6.1-sol`, same private T3, source at `ee1eaf8`, no repository or service changes) instrumented copies of the two cases. Its logs stay outside the repository because they hold raw T3 payloads.

### Restart reconciliation (T3-02)

- **Cause:** provider latency longer than the fixture's budget. The case hardcodes `stallMs: 60_000` for both coordinators and a 90 s test deadline. Production defaults to a 300 s stall window (`src/config.ts`).
- **Proof:** the unchanged copy failed again at 61.5 s. With `stallMs: 180_000` and a 300 s deadline the same case passed in 96.1 s. T3 moved the turn from `running` to `completed` with the expected `durable-fixture-ok` reply. The provider's first assistant item arrived about 92 s after the user message.
- **Not the cause:** the restarted coordinator reads plain HTTP snapshots (`src/coordinator.ts` default gateway); no watcher, F1/P2b/N2/H2 path or missed completion is involved.

### Rejection and interruption (SLK-04)

- **Cause:** Codex did not respond to the first prompt. After 180 s the turn and session were still `running`, with no assistant message, no activity, no pending approval and no `lastError`. The provider's own event log ends at the user message. The case fails at its first approval wait, before it declines or interrupts anything.
- **Control:** the accept-approval case on the same model passed in 9.8 s in the same session, so approvals still reach Agent Tag.
- **Not established:** why Codex stalled. No quota or API error was reported.
- **Agent Tag change:** none is supported by the evidence. Raising the Bun timeout alone would not help, because the case's own approval wait is 60 s.

### A stale assertion in the restart case

A Sonnet control finished the restarted turn in about 5 s and then failed at the reply assertion (`Expected durable-fixture-ok, Received ""`). The case assumes the second outbox row it claims is the final reply. Since F3 (`e31c19f`, #31) a status-message edit with an intentionally empty placeholder (`src/store/message-edits.ts`) can come second. The real outbox worker renders that correctly, so this is a test bug. The Codex pass above got the rows in the favourable order by chance.

### What has to happen

1. Test-only fix in `test/t3-live.integration.test.ts`: give the restart case a provider-sized stall budget and deadline, and find the final reply by the completed outcome's `outboxId` instead of claim order.
2. Re-run both cases. T3-02 can pass on the fixed suite. SLK-04's automated half needs Codex to answer the reject prompt, or the case to use a provider that does.

So each fixed case has passed on the real provider, but not yet in one clean full run. The GA matrix keeps T3-02 and SLK-04 off PASS until a full run of the fixed suite passes after the usage limit resets.
